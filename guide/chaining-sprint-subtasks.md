These options are set in the wizard and applied every time RepeatWise creates an issue. They all run as the schedule owner.

## Previous issue

In **Rules**, choose what to do if the previous issue is still open. The previous issue is the last issue RepeatWise created for this schedule. An issue in a "Done" status category is closed. Any other status counts as open.

- **Create anyway** (default). The new issue is always created.
- **Skip this occurrence.** If the previous issue is still open, no issue is created. The occurrence log shows it as skipped: "Skipped: the previous issue KEY-123 is still open." The schedule goes on to its next date.
- **Create and comment on the previous one.** The new issue is created. If the previous issue is still open, RepeatWise adds the comment "Next occurrence created: KEY-123", where KEY-123 is the new issue.
- **Create and move the previous one to a status.** The new issue is created. If the previous issue is still open, RepeatWise applies the workflow transition you picked. The picker reads the transitions from an issue of the selected type. The transition only works if the previous issue's status allows it.

The comment and the transition are never sent twice for one occurrence.

If the previous issue was deleted or the owner cannot see it, the new issue is created anyway, with a warning. If Jira rejects the comment or the transition, for example because the transition is no longer allowed, the new issue is kept and the occurrence log shows a warning. See [Errors](errors.html).

## Sprint

In **Rules**, pick a board with sprints. This works with Scrum boards and with team-managed boards that have sprints turned on. Kanban boards, and team-managed boards with sprints turned off, have no sprints.

RepeatWise adds each new issue to the active sprint of the board. If several sprints are active, it uses the one that started first. If no sprint is active, your choice applies:

- **Backlog.** The issue is not added to a sprint.
- **Next planned sprint.** The issue goes to the first planned sprint of the board, in the order of the board's backlog. If there is none, it stays in the backlog.

If the board or sprint cannot be found, or the owner cannot add issues to it, the new issue is kept and the occurrence log shows a warning. Sub-tasks follow their parent issue.

## Sub-tasks

**What** lets you add and reorder sub-task templates. Each has a summary, an optional description and an assignee choice of **Project default** (Jira's default assignee for the project, unassigned if the project has none) or schedule owner. Variables can be used in the text.

RepeatWise creates the sub-tasks under each new issue, in the order you set. It uses the sub-task issue type of the project. If a sub-task fails, RepeatWise retries it, and it searches Jira first so that no sub-task is created twice. If it still fails after the retries, the new issue and the sub-tasks already created are kept, the occurrence log shows the reason, and the schedule goes to **Error**.

## Not available

Parent issues, components, fix versions and custom fields are set under *Additional fields* on the first step (see [The wizard](wizard.html)). Sub-tasks do not get the parent's custom fields. [Service requests](service-requests.html) have no sub-tasks, sprint or custom fields; the previous-request rules work as for issues.
